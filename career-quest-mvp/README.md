# Career Quest — AI-навигатор развития сотрудника

Хакатон **HackAlem AI**, трек **Halyk Bank**, кейс **Career Quest**.

Веб-приложение, которое на основе профиля сотрудника, истории участия и
требований следующего грейда подбирает 1–3 релевантных шага развития с
**объяснимым** обоснованием (минимум 3 фактора), обновляет прогресс по навыкам
после выполнения активности и даёт HR срез по проседающим компетенциям.

Ядро продукта — движок рекомендаций (`backend/recommend.py`), а не интерфейс:
это простой, полностью объяснимый rule-based AI-слой (никаких "чёрных ящиков"),
специально спроектированный так, чтобы **не ломаться на однофакторных ловушках**
(см. раздел «Как это решает задачу жюри» ниже).

---

## 1. Быстрый запуск (одна команда)

Требования: Python 3.10+.

```bash
./run.sh
```

Скрипт сам создаст виртуальное окружение, поставит зависимости (только Flask),
сгенерирует стартовый датасет (если его ещё нет) и поднимет сервер на
**http://localhost:8000**.

Ручной запуск, если нужен контроль над шагами:

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cd backend
python3 generate_data.py   # один раз — сгенерировать data/*.json и .csv
python3 app.py              # http://localhost:8000
```

Открыть:
- `http://localhost:8000/` — представление **сотрудника**
- `http://localhost:8000/hr` — представление **HR**

## 2. Стек и архитектура

- **Backend:** Python 3 + Flask (единственная внешняя зависимость). REST API +
  раздача статики. Без базы данных — источник правды это JSON/CSV в `data/`,
  с персистентностью на диск при изменениях (MVP-уровень; см. «Дальнейшее
  развитие»).
- **AI-слой (объяснимые рекомендации):** `backend/recommend.py` — без внешних
  LLM-вызовов по умолчанию, что даёт: 100% воспроизводимость, нулевую
  задержку (<10 мс вместо допустимых 10 с из ТЗ) и полную объяснимость
  каждого балла рекомендации. Архитектура допускает опциональную LLM-надстройку
  для генерации более "человечного" текста обоснования поверх уже посчитанных
  факторов (см. «Дальнейшее развитие»).
- **Frontend:** ванильный HTML/CSS/JS без сборки и без внешних CDN-зависимостей
  — открывается и работает даже полностью офлайн, что исключает "ошибки на
  чужом ноутбуке" при воспроизведении жюри.
- **Данные:** синтетический стартовый датасет строго по объёмам ТЗ — 200
  профилей, 40 событий, 60 навыков, 24 месяца истории (см. раздел 4).

```
career-quest-mvp/
├── run.sh                      # запуск одной командой
├── requirements.txt
├── data/                       # стартовый датасет (генерируется скриптом)
│   ├── employees.json
│   ├── events.json
│   ├── skills.json
│   ├── activity_history.csv
│   └── test_profiles/
│       └── jury_test_profiles.json   # 3 "ловушки" для жюри (см. п.5)
├── backend/
│   ├── app.py                  # Flask API + раздача фронтенда
│   ├── recommend.py            # объяснимый рекомендательный движок + HR-аналитика
│   └── generate_data.py        # детерминированный генератор датасета (seed=42)
└── frontend/
    ├── index.html              # профиль сотрудника + рекомендации
    ├── hr.html                 # HR-дашборд
    ├── app.js
    └── styles.css
```

## 3. Основной сценарий (must-have из ТЗ)

| Требование ТЗ | Где реализовано |
|---|---|
| Профиль и карьерная траектория | `GET /api/employees/{id}` — роль, грейд, навыки, разрывы до следующего грейда, пройденные активности |
| AI-рекомендация следующего шага (1–3) | `GET /api/employees/{id}/recommendations` |
| Объяснение на ≥3 факторах | `recommend.py::_build_rationale` — грейд-разрыв, критичность навыка для роли, история участия (пропуски/отказы), стаж |
| Обновление прогресса | `POST /api/employees/{id}/complete` — пересчитывает уровень навыка по правилу `gain`/`max_level` из `events.json` и сразу возвращает обновлённые рекомендации |
| HR-view | `/hr` — проседающие компетенции, сотрудники без next step, участие по активностям |
| Загрузка доп. профилей на защите | `POST /api/import` + форма загрузки файла на `/hr` |
| Разграничение прав сотрудник/HR | Заголовки `X-Role` / `X-Employee-Id`; сотрудник видит только свой профиль (403 на чужой), HR-эндпоинты требуют `X-Role: hr` |
| Приватность вовлечённости | Участие/история недоступны другим сотрудникам — только владельцу профиля и HR |

**Сценарий сотрудника:** открыть `/`, ввести ID (например `E0001`) → видно
профиль, разрывы по навыкам до следующего грейда, 1–3 рекомендации с
обоснованием → нажать «Отметить выполненным» → прогресс и рекомендации
обновляются сразу.

**Сценарий HR:** открыть `/hr` → обзор компании, топ проседающих
компетенций, список сотрудников без рекомендованного шага, участие по
каждой активности (completed/skipped/declined).

## 4. Данные

Генерируются детерминированно (`seed=42`) скриптом `backend/generate_data.py`
и **строго соответствуют объёмам ТЗ**:

- `employees.json` — 200 профилей: 6 ролей × 4 грейда (Junior/Middle/Senior/Lead),
  у каждого — ролевые hard-навыки и общие soft-навыки, уровни 0–5.
- `events.json` — 40 событий (training / mentoring / rotation / assessment /
  workshop), у каждого — какие навыки развивает, на сколько (`gain`) и до
  какого потолка (`max_level`) — правило роста навыка, как требует ТЗ.
- `skills.json` — 60 навыков (48 hard, по 8 на роль + 12 общих soft),
  с требуемым уровнем по каждому грейду.
- `activity_history.csv` — 24 месяца истории участия, включая пропуски и
  отказы; у каждого сотрудника есть персональная склонность избегать один
  тип активности — это и создаёт реалистичные "ловушки" для рекомендателя.

Данные синтетические и не выносятся за пределы репозитория.

## 5. Как это решает задачу жюри (однофакторные ловушки)

ТЗ прямо описывает проверочный сценарий: *"у сотрудника ниже всего Public
Speaking, но по истории он трижды пропускал подобные активности, а для
перехода на следующий грейд критичен System Design"* — и рекомендация вида
*"бери минимальный навык"* здесь ошибается.

Движок считает score каждого навыка-кандидата как:

```
score = gap_до_грейда × вес_критичности − штраф_за_историю_пропусков
```

где `вес_критичности` выше для ролевых hard-навыков (прямой блокер грейда),
а `штраф_за_историю` растёт с числом пропусков/отказов именно по этому
направлению. Три готовых профиля-ловушки лежат в
`data/test_profiles/jury_test_profiles.json` — их можно загрузить прямо на
защите через форму на `/hr` (кнопка «Импортировать») либо через `POST
/api/import`, ID: `E9001`, `E9002`, `E9003`.

Проверено (см. вывод ниже): для `E9001` (Backend, Public Speaking = 0 и
трижды пропущен, System Design = 2 при требовании 4 для Senior) система
рекомендует **System Design** (score 3.0), а не Public Speaking (даже не
попадает в топ-3) — многофакторное правило отрабатывает корректно.

## 6. Ограничения соблюдены (п.9 ТЗ)

- Рекомендация никогда не строится на одном поле — обоснование всегда
  ссылается на разрыв по грейду, критичность роли и историю участия.
- Публичных рейтингов сотрудников нет и не планируется.
- Никакой механики вокруг обязательных процессов (типа очков за таймшиты).
- Только синтетические данные, реальных персональных данных нет.
- Геймификация не реализована как обязательная часть (её нет в MVP) —
  осознанно, согласно ТЗ она опциональна, а ядро — качество рекомендации.

## 7. Известные ограничения MVP и дальнейшее развитие

Это хакатон-MVP, сделан за ограниченное время. Прозрачно про то, что
упрощено:

- **Хранилище** — JSON/CSV-файлы вместо БД. Для прод-нагрузки нужен Postgres
  + миграции; сохранён чистый слой доступа к данным (`app.py` STORE), чтобы
  заменить его на БД без переписывания `recommend.py`.
- **Аутентификация** — роль передаётся заголовком (`X-Role`) для демо-режима
  вместо SSO/JWT. Точка расширения обозначена явно в `app.py::current_role`.
- **LLM-надстройка** — ядро не использует LLM намеренно (объяснимость,
  скорость, воспроизводимость). Естественное развитие — LLM поверх уже
  посчитанных факторов только для более живой формулировки rationale
  (не для самого решения) и для чат-интерфейса «спроси, почему тебе
  предложили этот шаг».
- **Опциональные фичи из ТЗ** (валюта/каталог наград, менторские механики,
  прогноз оттока, локализация на казахский, мобильная адаптация) — не
  реализованы в MVP, оставлены как потенциал развития согласно приоритету
  ТЗ (ядро — качество и объяснимость рекомендации).

## 8. Быстрая проверка вручную (curl)

```bash
# профиль сотрудника (только свой, роль employee)
curl -H "X-Role: employee" -H "X-Employee-Id: E0001" http://localhost:8000/api/employees/E0001

# рекомендации
curl -H "X-Role: employee" -H "X-Employee-Id: E0001" http://localhost:8000/api/employees/E0001/recommendations

# HR-обзор
curl -H "X-Role: hr" http://localhost:8000/api/hr/overview

# импорт проверочных профилей жюри
curl -X POST -H "X-Role: hr" -H "Content-Type: application/json" \
  --data @data/test_profiles/jury_test_profiles.json \
  http://localhost:8000/api/import
```
