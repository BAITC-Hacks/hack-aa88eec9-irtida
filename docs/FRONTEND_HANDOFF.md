## Что готово

- Новый русский интерфейс: изумрудная карта карьерного пути, текущий/следующий грейд, покрытие цели, квесты, навыки, история, личные достижения.
- Все разделы навигации работают. HR выбирает сотрудника из списка или поиска; из профиля можно вернуться в HR-обзор.
- Карточка квеста показывает тип активности, изменение навыков, прогноз покрытия цели и основания из `evidence`. Первый вариант раскрывает объяснение сразу.
- Подбор по правилам, AI, fallback, кэш и отсутствие кандидатов различимы. Провайдер/модель выводятся только при `mode=ai`.
- Выполнение: подтверждение в доступном диалоге → POST → только подтверждённые сервером навыки/история → сообщение о результате. Автоматического повторения POST нет.
- HR: дефициты, отсутствие доступного шага с причиной, completed/missed/declined, поиск профилей, JSON-импорт с отдельными dry-run и сохранением.
- Ошибки JSON/валидации/сети/HTTP/истёкшей сессии; быстрый индикатор ожидания; блокировка повторных кликов; timeout 15 секунд.
- Адаптация 1440/1024/768/360 px; фокус клавиатуры, skip-link, labels, progressbar, status/alert, поддержка reduced motion.
- Иконки — собственный inline SVG; шрифты системные. Внешние CDN, изображения и новые runtime-зависимости не добавлены.

## Как подключить к backend

Frontend использует относительный `/api/v1` и не обращается напрямую к OpenAI/NVIDIA. Сессионная cookie — HttpOnly, `credentials: same-origin`. В запросах сохранены `Content-Type: application/json` и `X-Requested-With: CareerQuest`. Ключи должны остаться на сервере.

Для локальной разработки сохранён Vite proxy `/api` → `http://127.0.0.1:8000`. При раздельном deployment нужен reverse proxy с общим origin: простая смена URL на другой домен не обеспечивает работу cookie/CSRF.

| Method / URL (после `/api/v1`) | Использование UI | Ожидаемый результат |
| --- | --- | --- |
| `GET /auth/me` | Восстановление сессии при открытии | `{ role: "employee" | "hr", employee_id: string | null }`; 401 для отсутствующей сессии |
| `GET /auth/demo-accounts` | Профили демо-входа без действующей сессии | `{ enabled, accounts: [{ id, label, role }] }` |
| `POST /auth/demo` | Вход, body `{ "account": "E001" }` | Account + сессионная cookie |
| `POST /auth/logout` | Выход | JSON либо HTTP 204 |
| `GET /employees` | HR-список и переключение профилей | Массив Employee |
| `GET /employees/{id}` | Профиль и восстановление прогресса | Profile |
| `POST /employees/{id}/recommendations` | Подобрать/обновить квесты, без body | Recommendations |
| `POST /employees/{id}/events/{event_id}/complete` | Подтверждение выполнения, без body | `{ profile: Profile, already_completed: boolean }` |
| `GET /hr/overview` | Три обязательных среза | Metrics |
| `POST /imports?dry_run=true` | Проверка выбранного JSON | ImportSummary, база не изменяется |
| `POST /imports?dry_run=false` | Сохранение точно того же проверенного JSON | ImportSummary |

IDs в URL кодируются `encodeURIComponent`. Авторизацию, роль, допустимость активности, идемпотентность и рост навыков обязан проверять backend; скрытые кнопки не являются защитой.

### Profile и рекомендации

Актуальные TypeScript-типы находятся в `web/src/api.ts`. Нужны стабильные поля:

```text
Profile
  employee: { id, name, role, grade, tenure_months, skills: Record<string, number> }
  trajectory:
    next_grade: string | null
    coverage: number | null                # процент 0–100, НЕ доля 0–1
    status: string
    skills: [{ id, name, level: number | null, required, gap: number | null }]
  available: Candidate[]
  history: [{ id, title, status, occurred_at }]
  recommendation?: Recommendations | null

Candidate
  id, title, type
  changes: Record<skill_id, { name, before, after, gain }>
  evidence: [{ factor, text }]

Recommendations
  items: Candidate[]
  mode: "ai" | "rules" | "fallback" | "no_candidates"
  cached: boolean
  reason: string | null
  provider: string | null
  model: string | null
  elapsed_ms: number
```

Минимальный пример ответа recommendation:

```json
{
  "items": [{
    "id": "EV_DESIGN",
    "title": "Практикум по архитектуре",
    "type": "workshop",
    "changes": {
      "SK_SYSTEM_DESIGN": { "name": "System Design", "before": 2, "after": 3, "gain": 1 }
    },
    "evidence": [
      { "factor": "grade", "text": "Middle → Senior: ваш карьерный ориентир." },
      { "factor": "skill_gap", "text": "System Design 2 при требуемых 4." },
      { "factor": "history", "text": "В истории есть успешный практикум этого формата." }
    ]
  }],
  "mode": "rules",
  "cached": false,
  "reason": null,
  "provider": null,
  "model": null,
  "elapsed_ms": 12
}
```

Пример иллюстрирует контракт, не является рекомендацией для реального профиля. `evidence.text` должен строиться по фактам конкретного сотрудника; UI не придумывает недостающие факторы. Неизвестный `factor` отображается как «Основание рекомендации». Известные типы активностей переведены в `view-model.ts`; неизвестные типы выводятся как пришли.

### Правила расчётов и геймификация

- Авторитетный `coverage` приходит с backend. UI не меняет грейд при 100%.
- Прогноз карточки использует только серверные `changes.after` и требования: `100 × sum(min(after_or_current, required)) / sum(required)`, округление до целого. Это preview до выполнения, не запись данных.
- При неизвестном уровне любого целевого навыка или `coverage=null` прогноз не показывается. Неизвестный уровень рисуется отдельным состоянием, а не нулевым прогрессом.
- При изменении формулы покрытия на backend нужно синхронно согласовать `projectedCoverage()` либо вернуть готовый `projected_coverage` как совместимое расширение. Сейчас такого поля UI не требует.
- После completion UI заменяет профиль полным ответом сервера. В ответе нужны актуальная история, навыки, available и корректно инвалидированная recommendation. `already_completed=true` не вызывает сообщение о повторном росте.
- Достижения вычисляются на клиенте без БД: первая completed-запись, три completed-записи, хотя бы один известный `gap=0`. Пропуски и отказы не учитываются как успех и не штрафуются.
- Нет XP, валюты, streaks, публичных рейтингов или автоматических повышений. Карта пути — иллюстрация последовательности, а не дополнительная система начислений.
- История должна приходить полностью для корректного счётчика достижений. Если backend вводит пагинацию, передайте отдельно totals и согласуйте изменение UI. Сейчас UI сохраняет порядок history из ответа.

### HR и импорт

`Metrics` содержит:

```text
employee_count
gaps: [{ name, affected, eligible, unknown, percent: number | null }]
no_step: [{ id, name, reason }]
participation: [{ id, title, completed, missed, declined }]
```

`percent=null` не превращается в 0%; число неизвестных оценок показывается отдельно. `no_step.reason` поддерживает `no_grade_rule`, `missing_skills`, `no_eligible_activity`.

JSON-импорт ожидает `{ employees_added, history_added }` в обоих ответах. Дополнительные поля не мешают. При dry-run эти числа означают прогноз добавления; при сохранении — реальные добавления. При замене файла кнопка сохранения снова блокируется до проверки. Backend обязан повторно валидировать файл при сохранении и выполнять запись атомарно: dry-run сам по себе не гарантирует отсутствие конфликтов к моменту POST.

**Для официального кита ещё нужен согласованный контракт.** Этот UI намеренно сохраняет `demo-v1`, а не угадывает multipart endpoint для employees/events/skills/history. Backend-агенту нужно передать в своём handoff:

1. URL, HTTP method и Content-Type импорта оригинальных файлов.
2. Имена полей multipart либо JSON-envelope, допустимые файлы и ограничения размера.
3. Формат dry-run: добавленные/пропущенные записи, предупреждения, ошибки с файлом и строкой.
4. Поведение повторного импорта и конфликтов, а также пример запроса без закрытого датасета.

После этого расширить только импорт в `HrView.tsx` и API-клиент. Для FormData нельзя принудительно ставить `Content-Type: application/json`: браузер должен добавить multipart boundary. Текущий `api()` предназначен для JSON.

### Ошибки, задержки, повторные действия

- HTTP 401 завершает локальное представление сессии и возвращает демо-вход.
- HTTP 422 `{ detail: [{ loc, msg }] }` отображает путь поля и сообщение. Строковый `{ detail }` также поддерживается.
- Ответ proxy в HTML превращается в понятную ошибку HTTP; тело HTML не показывается пользователю.
- Timeout клиента — 15 секунд. Цель из ТЗ для AI остаётся до 10 секунд, её обязан обеспечить backend. UI показывает ожидание сразу, а после 8 секунд меняет сообщение. Сам интерфейс не гарантирует SLA модели.
- POST не повторяется автоматически после тайм-аута: действие могло сохраниться на сервере. Есть «Обновить данные»; completion всё равно должен оставаться идемпотентным на backend.
- AI недоступен: backend возвращает `mode=fallback`, а не `mode=ai`. Сохранённая рекомендация должна иметь `cached=true` независимо от способа получения.
- Персональные ответы и сессия не записываются в localStorage. Отсутствие внешних ресурсов позволяет уже собранному UI работать с локальным backend без интернета; полный offline после закрытия вкладки без работающего сервера не реализован.

## Проверки

На существующих установленных зависимостях:

```sh
cd web
npm test
npm run build
```

Результат: **10/10 автоматических тестов прошли**, TypeScript и production build прошли. Новые зависимости не добавлены; lockfile не менялся. Повторная установка пакетов не требовалась.

Автотесты: прогноз и неизменность исходного профиля; ограничения покрытия; неизвестные навыки; достижения; подписи режимов; cookie/CSRF; 422/401/204/HTML; отсутствие сети; timeout и отсутствие автоматических повторов POST.

Браузерные проверки выполнены:

- Действующий API на 8000: HR-обзор и открытие существующего профиля.
- Изолированный frontend-стенд: employee login → recommendation → четыре фактора → completion с клавиатуры → рост 55% → 64%, System Design 2 → 3 → достижение → reload сохраняет состояние в памяти тестового сервера.
- На стенде проверены AI (имитация), cached AI после reload, rules, fallback, no_candidates, неизвестный навык, 9-секундный ответ и блокировка повторной кнопки, ошибка HTTP 503.
- HR: три среза, неизвестная доля, поиск, переход в профиль и назад, 422 при неверном файле, dry-run, отдельное подтверждение импорта.
- На 1440/1024/768/360 px профиль не переполняет страницу; HR дополнительно проверен на 1024/768/360 px. На 360 px широкая таблица прокручивается внутри контейнера.
- Кнопки имеют доступные имена, диалог получает фокус, Tab → Enter завершает тестовый квест. В проверенном стенде ошибок JS в консоли нет.
- Frontend-файлы проверены на распространённые форматы API-ключей/private key; `git diff --check -- web` прошёл.

Стенд для воспроизведения UI без работы backend-агента:

```sh
cd web
npm run build
npm run test:preview
# http://127.0.0.1:8011
```

`tests/preview-server.mjs` — только тестовая имитация API, не замена FastAPI. Он не сохраняет данные после перезапуска, импорт только имитирует, AI не вызывает. В приложение при production build не включается. Fixtures созданны для UI и не являются официальным китом.

В sandbox Windows запуск Vite dev завершился ошибкой доступа esbuild к родительским каталогам; production build и выдача собранного UI действующим локальным сервером работают. Из-за этого визуальные проверки сделаны на production build. Никакие настройки backend ради этого не менялись.

## Объединение веток

Сначала backend-агент должен закончить собственный коммит. В общей рабочей папке сейчас лежат изменения двух агентов: **не использовать `git add .` для backend-коммита**, добавлять его файлы явно. Frontend уже опубликован отдельно. Удобнее проводить объединение в новом clone/worktree, чтобы не затронуть текущую незавершённую работу.

В чистом checkout:

```sh
git fetch origin
git switch -c integration/career-quest origin/feature/career-quest-mvp
git merge origin/work/backend-kit-ai
git merge origin/work/frontend-ux
```

Затем установить зависимости по инструкциям backend-агента и выполнить его test suite, `cd web && npm test && npm run build`. Запустить общий продукт стандартной командой из README и пройти реальный end-to-end сценарий с импортом кита и настоящей AI-рекомендацией. Frontend-агент backend-тесты во время параллельной разработки не запускал и ветки не объединял.

1. Подключить согласованный импорт оригинального кита. Сейчас в UI только существующий JSON/demo-v1.

5. Графические достижения опциональны по ТЗ; главное — обоснованная рекомендация и реальный прогресс. Voice Router и ограничение ответа голосового робота до секунды относятся к отдельному кейсу, голосовой интерфейс здесь не добавлен.
