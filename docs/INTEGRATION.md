# Интеграция Career Quest

Итоговая рабочая ветка: `work/career-quest-integration`. Репозиторий: `BAITC-Hacks/hack-aa88eec9-irtida`. Документ описывает общий контракт frontend/backend и официального Career Quest Kit 1.0. Backend является источником данных, допустимости действий и результатов расчёта.

[BACKEND_HANDOFF.md](BACKEND_HANDOFF.md) и [FRONTEND_HANDOFF.md](FRONTEND_HANDOFF.md) сохранены как исторические отчёты отдельных веток. Их числа тестов и ограничения UI относятся к состоянию до интеграции; результаты текущего прогона фиксируются отдельно ниже. Инструкции запуска находятся в [README](../README.md), сценарий защиты — в [DEMO.md](DEMO.md).

## Данные и ограничения

Официальный набор задаёт дату моделирования **2026-10-01** и шкалу навыков **0–5**. Отсутствующий навык kit-v1 равен 0, а в demo-v1 остаётся неизвестным. Уровни восстанавливаются от последней оценки: только `completed` строго после `last_review_date` дают прирост; в полном наборе таких записей 318. Повторный импорт не повторяет начисления и не сбрасывает завершения через API.

Четыре mandatory-события исключены из рекомендаций. 544 участия в обязательных событиях после уже завершённого такого события противоречат общему правилу README кита. Они сохранены с предупреждением `mandatory_history_repeated_after_completion`; исключение разрешено только для mandatory с пустыми эффектами. Оно не разрешает повтор добровольных событий и не начисляет навыки.

Повторяемый клуб `EV_036` использует дату выбранной сессии как `occurrence_id`. Клиент получает её от сервера и возвращает при completion; повтор этого occurrence безопасен, произвольная/устаревшая незавершённая сессия отклоняется. Новая сессия — отдельное завершение. Scheduled-завершения моделируются датой сессии, self-paced — датой среза.

Покрытие и двойной вес critical-разрыва — прозрачные расчёты приложения, а не дополнительные требования организаторов. Coverage не меняет грейд. Модель выбирает 1–3 допустимых ID, объяснения и числовой прогресс вычисляет backend. Личные достижения не влияют на навыки и не образуют публичный рейтинг.

При первой загрузке из HR `replace_demo=true` разрешён только для исходного неизменённого demo и всех четырёх файлов. При изменённой базе нужен новый DATABASE_URL, чтобы сохранить прогресс. Дополнения kit-v1 принимаются без replace_demo: employees.json и/или activity_history.csv с исходными схемами. Конфликты ID и ссылок отклоняют весь запрос. Размер multipart ограничен 5 000 000 байт, включая служебные данные.

## Авторизация и AI

Frontend обращается только к `/api/v1` с `credentials: same-origin`. Сессия хранится в HttpOnly / SameSite=Strict cookie. POST требует `X-Requested-With: CareerQuest` и разрешённого Origin. Для раздельного размещения нужен общий origin через reverse proxy. Сотрудник не может читать чужие профили или HR; HR не может завершать события за сотрудника.

401 завершает локальное представление сессии. 403 означает отсутствие права или неверный Origin/header; 409 — конфликт расчёта/профиля; 413 — большой запрос; 415 — неверный формат; 422 — невалидные данные/доступность; 429 — лимит; 503 — временная недоступность. POST completion/import не повторяется автоматически после ошибки: сначала обновить данные.

`AI_DATA_POLICY_APPROVED` передаётся из окружения в backend `cloud_data_approved`, включая Docker Compose. Пока значение не true, облачный запрос не выполняется. Включение допустимо только при разрешённой обработке данных выбранным провайдером; этот флаг не снимает ограничений организаторов. Ключи не должны попадать в frontend, VITE_*, вывод команд, fixtures или Git. Режим rules работает без ключа; fallback честно сообщает о недоступности/невалидности AI или запрете передачи.

## Воспроизводимые проверки

Активировать Python-окружение, установить `server/requirements-dev.txt`, установить web-зависимости через `npm --prefix web ci`. Из корня:

```sh
python -m pytest -q
python -m pip check
npm --prefix web test
npm --prefix web run build
git diff --check
```

Для локальной проверки полного официального набора на Windows:

```powershell
$env:CAREER_QUEST_KIT_DIR=(Resolve-Path 'career_quest_dataset/case_1/career_quest_dataset').Path
python -m pytest -q
```

На Linux/macOS переменная задаётся командой `export CAREER_QUEST_KIT_DIR=/absolute/path/to/kit`. Без неё проверки внешнего кита пропускаются. Если старый pytest temp имеет несовместимые ACL, используйте новый каталог внутри игнорируемого data/private: `python -m pytest -q --basetemp=data/private/pytest-integration-run -p no:cacheprovider`. Не выбирайте каталог, содержащий нужные файлы: pytest управляет своим basetemp.

CI запускает backend pytest + pip check и frontend npm test + build. Он не включает закрытый kit, настоящие AI-ключи или браузерную имитацию как доказательство live API.

Воспроизводимый HTTP-прогон через настоящий frontend API-клиент:

```powershell
$env:CAREER_QUEST_KIT_DIR=(Resolve-Path 'career_quest_dataset/case_1/career_quest_dataset').Path
npm --prefix web run test:integration
```

Скрипт сам запускает FastAPI с отдельной временной SQLite, использует `importKit` и `completeEvent` из `web/src/api.ts`, проверяет реальные JSON-ответы TypeScript-компилятором и перезапускает сервер. Исходный Kit читается по локальному пути; временные данные остаются в игнорируемом `web/.test-build` и удаляются после успеха. Без переменной команда явно сообщает `SKIP`. Для другого Python можно задать абсолютный `CQ_PYTHON`. Это HTTP-интеграция, а не браузерный E2E.

Совместный сценарий проверяется на **отдельной SQLite**, реальном FastAPI и собранном frontend:

1. Задать новый DATABASE_URL, запустить приложение. Войти как HR.
2. Через UI выполнить kit dry-run + replace_demo: отсутствие записи, правильные счётчики, предупреждение 544. Подтвердить импорт, проверить 200 сотрудников.
3. Повторить импорт без replace_demo: нулевые добавления и сохранённый прогресс. Проверить 422 для невалидного дополнительного файла, затем успешный импорт маленького независимого профиля/истории.
4. Открыть профиль: правильные навыки после 318 завершений, critical, следующий грейд. Проверить Lead, все статусы истории и причины no_step.
5. Войти сотрудником, получить recommendations в rules/fallback, проверить минимум три фактора и отсутствие mandatory. При разрешённом live AI отдельно проверить ai, provider/model и время; при повторе — cached.
6. Выполнить обычное событие, проверить профиль/навыки/историю из ответа, инвалидирование рекомендаций. Повтор запроса не меняет навыки.
7. Выполнить сессию EV_036 с occurrence_id; повторить тот же occurrence, затем следующую доступную сессию. Прирост начисляется один раз на сессию.
8. Перезагрузить страницу и перезапустить backend с той же БД; проверить сохранение данных. Вернуться в HR, проверить агрегаты без двойного no_show/missed.
9. Проверить cookie/401/403, console/network, отсутствие автоматически повторённых POST и времена ответа. Для latency отделять реальные вызовы от кэша и имитации.

## Оставшиеся границы продукта

DEMO_MODE — локальный синтетический вход, не production-auth. SSO, полная казахская локализация, миграции/PostgreSQL и денежный учёт AI не реализованы. Отсутствие облачного ключа не блокирует основной сценарий rules/fallback. Фактические непроверенные окружения и неустранённые ошибки должны быть указаны вместе с результатами финального прогона.
