## Твоя область

Можно изменять:

- `server/**`
- backend-тесты
- `.env.example`, только если нужны новые пустые переменные
- собственные синтетические fixtures с префиксом `examples/backend-`
- новый `docs/BACKEND_HANDOFF.md`

Не изменяй:

- `web/**`
- `README.md`, `TASKS.md`, `Dockerfile`, `compose.yaml`, CI во время параллельной работы
- файлы frontend-агента

Никогда не коммить `.env`, API keys, токены, локальные БД, логи, реальные персональные данные, официальный закрытый датасет или файлы стартового кита. До commit выполни проверку секретов и `git status --ignored --short`.

## P0. Официальный импорт

1. Реализуй импорт исходных `employees.json`, `events.json`, `skills.json`, `activity_history.csv` без ручного преобразования пользователем.
2. Поддержи полный набор и дополнительные проверочные профили/историю в том же формате.
3. Сохрани атомарный dry-run и понятные ошибки: файл, строка или JSON path, причина.
4. Не создавай дубли при повторной загрузке. Конфликт существующей записи не перезаписывай молча.
5. Проверь ссылки employee/event/skill, диапазон навыков 0–5, статусы, даты, `gain`, `max_level` и аудиторию события.
6. Не начисляй исторические активности повторно, если skills уже являются текущим снимком. Это решение принять только после чтения README кита.
7. Если правила повторных прохождений заданы, используй occurrence/history ID для идемпотентности; не запрещай повтор события без основания в ките.
8. Сохрани поддержку текущего `demo-v1` для локального fallback или явно мигрируй fixtures и тесты.

## P0. Прогресс и рекомендации

1. Сверь определение следующего грейда и расчёт прогресса с китом.
2. Сервер детерминированно считает skill gaps, eligibility, ожидаемый и фактический прирост. LLM не меняет эти числа.
3. Не считай отсутствующий навык нулевым без правила кита.
4. Рекомендация выбирает 1–3 существующих доступных event IDs и учитывает текущий грейд, разрывы навыков, историю completed/missed/declined и требования следующего уровня.
5. Проверь ответ модели: только допустимые IDs, без дублей, без придуманных фактов. Числовое объяснение формируй из проверенных серверных данных.
6. Не делай правило «выбрать минимальный навык». Добавь контрастный тест: Public Speaking ниже всех, но важнее System Design и похожие speaking-события ранее пропускались.
7. При timeout/ошибке/невалидном JSON верни явно обозначенный `fallback`; кэш помечай `cached=true`.
8. Сохрани общий лимит AI до 10 секунд. Не жди последовательно два полных timeout.

## P0. Живой AI

1. Доведи OpenAI provider до живого проверенного запроса с `gpt-4.1-mini` или другой доступной дешёвой моделью, если аккаунт её не предоставляет.
2. Ключ читается только из `.env`/environment backend. Не проси вставлять ключ в чат и не выводи его в логах.
3. Зафиксируй Structured Outputs/JSON validation, `store=false`, max tokens, timeout и нулевую/низкую temperature.
4. NVIDIA проверь только после полного P0. Если времени мало, оставь его документированным резервом и не трать время на автоматический failover.
5. Учёт токенов/стоимости добавляй только после рабочего сценария. Не выполняй массовые платные запросы.
6. Перед отправкой данных к облачной модели проверь ограничения организаторов. Используй только синтетические/разрешённые данные.

## P0. HR и безопасность

1. Проверь обязательные агрегаты на полном наборе: частые skill gaps, сотрудники без доступного шага с причиной, участие по событиям.
2. Не смешивай неизвестное значение навыка с нулём.
3. Сохрани серверное разграничение employee/HR и запрет HR завершать активность за сотрудника.
4. Сохрани транзакционность, защиту от двойного начисления, проверку Origin и rate limits.
5. DEMO_MODE остаётся только локальным режимом на синтетике. Не делай его безопасным для публичного production-доступа без полноценной auth.

## API-контракт

Не ломай существующие URL и поля, используемые `web/src/api.ts` и `web/src/main.tsx`:

- `GET /api/v1/employees/{id}` возвращает `employee`, `trajectory`, `history`, `available`, `recommendation`.
- `POST /api/v1/employees/{id}/recommendations` возвращает `items`, `mode`, `reason`, `cached`, `provider`, `model`, `elapsed_ms`.
- Каждый item содержит `id`, `title`, `type`, `changes`, `evidence`.
- `POST /api/v1/employees/{id}/events/{event_id}/complete` возвращает обновлённый `profile` и `already_completed`.
- `GET /api/v1/hr/overview` сохраняет `employee_count`, `gaps`, `no_step`, `participation`.

Импорт можно расширить отдельным multipart endpoint, но текущий `POST /api/v1/imports` не удаляй. Все изменения контракта опиши в handoff, не редактируя frontend.
