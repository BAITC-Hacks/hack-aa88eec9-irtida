# Career Quest

AI-навигатор развития сотрудника для HackAlem AI, трек Halyk Bank: профиль → объяснимый следующий шаг → выполнение → прогресс → HR-срез. React и FastAPI работают с официальным Career Quest Kit 1.0 и дополнительными профилями жюри. По умолчанию приложение работает локально без API-ключей в явно обозначенном режиме `rules`.

Сценарий защиты: [docs/DEMO.md](docs/DEMO.md). Контракты, проверки и ограничения интеграции: [docs/INTEGRATION.md](docs/INTEGRATION.md). Исходные [BACKEND_HANDOFF.md](docs/BACKEND_HANDOFF.md) и [FRONTEND_HANDOFF.md](docs/FRONTEND_HANDOFF.md) сохранены как отчёты отдельных веток до интеграции; текущая инструкция имеет приоритет над их устаревшими ограничениями.

## Запуск одной командой

Из корня репозитория с установленным Docker Compose:

```sh
docker compose up --build
```

Открыть **http://127.0.0.1:8000**. SQLite хранится в томе `quest-data`. Первый запуск создаёт небольшой синтетический demo-v1; официальный набор загружается через HR-интерфейс. Кит и секреты исключены из Docker build context. Первичная сборка требует интернета; перед защитой подготовьте зависимости и образ. Фактический статус проверки Docker указан в [отчёте интеграции](docs/INTEGRATION.md).

Без Docker нужны Python 3.11+ и Node.js 22+:

```sh
python run.py
```

Скрипт создаёт `.venv`, устанавливает недостающие зависимости, собирает frontend и запускает FastAPI на `127.0.0.1:8000`. На Windows также доступно `./run.ps1`; если Python не в PATH, используйте `./run.ps1 -PythonExe 'C:\path\to\python.exe'`. Остановка — Ctrl+C. После обновления уже установленного проекта обновите Python-зависимости командой `python -m pip install -r server/requirements-dev.txt` в активированном `.venv`.

Если порт 8000 занят, выберите свободный порт. Для входа и других POST на новом порту добавьте его origin в `ALLOWED_ORIGINS` (launcher не меняет явные настройки окружения или `.env`):

```powershell
$env:ALLOWED_ORIGINS='http://localhost:8017,http://127.0.0.1:8017'
python run.py --port 8017
```

Открыть http://127.0.0.1:8017. PowerShell-обёртка принимает `./run.ps1 -Port 8017`. На Linux/macOS эквивалент: `ALLOWED_ORIGINS=http://localhost:8017,http://127.0.0.1:8017 python run.py --port 8017`. Допустимый порт — 1–65535. Для одновременной работы с Vite добавьте также его origin `http://127.0.0.1:5173` в список.

Для отдельной репетиции сохраните рабочую базу и задайте новый путь перед запуском:

```powershell
$env:DATABASE_URL='sqlite:///./data/private/rehearsal.db'
python run.py
```

В Compose путь БД фиксирован внутри тома. Отдельный проект Compose создаёт отдельный том: `docker compose -p career-quest-rehearsal up --build` (сначала освободите порт 8000).

## Основной сценарий

1. Войти как HR и импортировать официальный набор по инструкции ниже.
2. Открыть любого сотрудника: роль, грейд, навыки, историю и требования следующего грейда. Критические навыки выделены отдельно.
3. Войти как этот сотрудник и запросить 1–3 шага. Объяснение содержит текущий грейд, разрыв навыков, требования следующего уровня и историю участия.
4. Выполнить доступную активность. Сервер возвращает обновлённые навыки, историю и траекторию. Перезагрузка сохраняет результат; повторное выполнение того же события или сессии не начисляет прирост повторно.
5. Вернуться в HR: дефициты компетенций, сотрудники без доступного шага с причинами, участие по мероприятиям.

Для короткой репетиции без кита можно использовать «Сотрудник 01»: в режиме `rules` архитектурный практикум приоритетнее самого низкого Public Speaking благодаря требованиям Senior и истории. Данные `examples/` — отдельные синтетические примеры, не официальный набор.

## Импорт официального кита и профилей жюри

Кит остаётся локальным входным набором и не включается в Git. Поддерживается исходная схема без ручного преобразования. В этой рабочей папке файлы лежат в `career_quest_dataset/case_1/career_quest_dataset/`; на другой машине выберите каталог выданного кита.

В HR выберите импорт Career Quest Kit и четыре оригинальных файла:

| Имя файла | Содержание |
| --- | --- |
| `skills.json` | `{meta, proficiency_scale, skills, role_profiles}` |
| `employees.json` | `{meta, employees}` |
| `events.json` | `{meta, events}` |
| `activity_history.csv` | Исходные колонки `record_id,employee_id,event_id,date,due_date,status,completion_pct,score,feedback_rating,assigned_by` |

Порядок загрузки:

1. Для первой загрузки вместо автоматически созданного demo включить замену исходного demo (`replace_demo`). Она разрешена только пока demo не изменён импортами или выполнениями. Если прогресс уже есть, используйте новую БД.
2. Выбрать файлы и запустить проверку (`dry_run=true`). Проверка ничего не сохраняет. Изменение файлов или флага замены требует новой проверки.
3. Просмотреть счётчики, предупреждения и ошибки. Для полного набора ожидаются **200 сотрудников, 60 навыков, 40 событий, 2 743 записи истории**, `completed_after_review=318` и предупреждение о **544** повторных участиях в обязательных мероприятиях.
4. После успешной проверки подтвердить импорт. Backend повторно валидирует данные и сохраняет их одной транзакцией. Обновляются HR-обзор, список сотрудников и доступные аккаунты. Старая employee-сессия при замене demo отзывается; текущая HR-сессия сохраняется.

Дополнительные профили жюри загружаются тем же способом **без замены demo**, когда база уже содержит kit-v1. Достаточно `employees.json` и/или `activity_history.csv`; справочники повторять не обязательно. Сохраняйте оригинальную оболочку JSON с `meta`, имена файлов и колонки CSV. Менеджеры и остальные ссылки должны существовать в базе либо поступать в том же импорте.

Точное повторение файла не создаёт дубли. Изменённая запись с прежним ID, некорректное поле или неизвестная ссылка отклоняют весь запрос. Исходные оценки и история хранятся локально; новая история пересчитывает навыки от оценки, сохраняя завершения через приложение. `completed_after_review` — число завершений после оценки во всём собранном состоянии, а не число новых начислений.

API: `POST /api/v1/imports/kit?dry_run=true|false&replace_demo=true|false`, multipart-поле **`files`**, от одного до четырёх файлов, до **5 000 000 байт** на весь запрос. Браузер сам задаёт `Content-Type` и boundary. Ошибки содержат `detail` и, при наличии, `errors: [{source, path, reason}]`. Старый Pydantic `detail: [{loc, msg}]` также поддерживается.

Для загрузки до запуска приложения можно использовать CLI в активированном окружении:

```powershell
$env:DATABASE_URL='sqlite:///./data/private/official-demo.db'
python -m server.app.import_kit_cli 'career_quest_dataset/case_1/career_quest_dataset' --dry-run
python -m server.app.import_kit_cli 'career_quest_dataset/case_1/career_quest_dataset'
python run.py
```

CLI не создаёт demo и не отправляет данные в сеть. Для существующего неизменённого demo у него есть `--replace-demo`. Старый JSON-импорт `POST /api/v1/imports` сохранён для `demo-v1`, например `examples/additional-profile.json`. Форматы demo-v1 и kit-v1 не смешиваются в одной базе.

## Правила прогресса и рекомендаций

- «Сегодня» в официальном наборе — **2026-10-01**, независимо от системных часов. Отсутствующий навык равен **0**; в старом demo-v1 отсутствующая оценка остаётся неизвестной.
- Исходные уровни относятся к `last_review_date`. Учитываются завершения строго после этой даты; в полном наборе их **318**. Завершения до оценки и в день оценки повторно не начисляются.
- Прирост вычисляется сервером: `max(0, min(gain, max_level - current, 5 - current))`.
- Траектория следует Junior → Middle → Senior → Lead в текущей роли и использует требования **следующего** грейда. Для Lead показывается `highest_grade`. `career_goal` сохраняется как контекст.
- Покрытие — `100 × sum(min(current, required)) / sum(required)`, округлённое до целого. Это показатель приложения, а не формула повышения из кита. **100% не повышает грейд автоматически**; критические требования отображаются отдельно.
- Четыре обязательных мероприятия не рекомендуются как добровольные шаги. Проверяются роль, грейд, prerequisites, доступная будущая сессия, полезный прирост и история завершений.
- Алгоритмический подбор учитывает сокращение разрыва, критические навыки и историю типа/формата. Двойной вес critical-разрыва — объяснимое решение приложения, а не правило организаторов.
- Повторяемое добровольное событие — только `EV_036`. Для него нужен `occurrence_id` из текущей карточки; повтор той же сессии возвращает `already_completed=true`. Следующие сессии появляются последовательно. Для scheduled-события завершение записывает дату сессии, для self-paced — дату среза: это симуляция кита.

В исходной истории есть расхождение с правилом однократного завершения: **544 участия в mandatory-событиях после уже завершённого такого события**. Импорт сохраняет эти записи и возвращает `mandatory_history_repeated_after_completion`. Исключение разрешено только обязательным событиям с пустыми эффектами; повторный прирост не возникает, добровольные повторы не разрешаются.

История сохраняет `completed`, `in_progress`, `dropped`, `no_show`, `declined`, `overdue` и старый `missed`. В HR совместимое поле `missed` уже включает `no_show`: они не складываются повторно. HR считает записи участия, а не уникальных участников.

## AI и честное отображение режима

Ключи хранятся только в backend `.env` или environment. Скопируйте `.env.example` в `.env` и настройте провайдера локально: `AI_PROVIDER=openai` с `OPENAI_MODEL` и `OPENAI_API_KEY` либо `AI_PROVIDER=nvidia` с `NVIDIA_MODEL` и `NVIDIA_API_KEY`. Не используйте `VITE_*` для секретов.

`AI_DATA_POLICY_APPROVED=true` включает серверный `cloud_data_approved`. Устанавливайте его только для данных, которые разрешено передавать выбранному облачному провайдеру. Синтетичность кита сама по себе не отменяет условия организаторов о передаче данных. Пока флаг выключен, облачный вызов не выполняется и интерфейс показывает причину fallback. Этот флаг не выдаёт разрешение будущим загрузкам с реальными данными.

После изменения настроек перезапустите приложение; в Docker выполните `docker compose up -d`. По умолчанию используется `rules`, разрешение на передачу выключено. Compose передаёт флаг разрешения в backend.

| Ответ backend | Значение в UI |
| --- | --- |
| `mode=ai`, `cached=false` | Свежий проверенный ответ модели, с provider/model |
| `cached=true` | Сохранённый ответ соответствующего режима; `elapsed_ms` относится к исходному расчёту |
| `mode=rules` | Алгоритмический подбор без обращения к LLM |
| `mode=fallback` | AI не вызван или недоступен/невалиден; показан подбор по правилам и причина |
| `mode=no_candidates` | Доступных шагов нет; это корректное пустое состояние |

Сервер сначала формирует допустимые активности. Модель выбирает 1–3 уникальных ID из этого списка; сервер валидирует ответ и возвращает объяснения из фактических данных. Имя/ID сотрудника и сырая история в prompt не включаются. OpenAI использует JSON Schema и `store=false`; последнее не является гарантией Zero Data Retention.

Бюджет provider-вызова по умолчанию 7 секунд, максимум 8; кэш — 1 час, fallback — 30 секунд. Квоты: 6 запросов/минуту на профиль и 300 за скользящие 24 часа на приложение. Это лимиты запросов, не денежный бюджет. Автоматического переключения облачных провайдеров нет. ТЗ требует UI до 2 секунд и AI до 10 секунд; фактические замеры и непроверенные условия указаны в отчёте интеграции.

Для одного явного live smoke на встроенном синтетическом профиле после локальной настройки провайдера:

```sh
python -m server.app.ai.smoke --synthetic
```

Обычные тесты не используют сеть или ключи. Live-вызов, Docker и браузерная проверка не считаются выполненными по результатам имитации: смотрите [актуальные результаты](docs/INTEGRATION.md).

## Разработка и проверки

```sh
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
python -m pip install -r server/requirements-dev.txt
python -m uvicorn app.main:app --app-dir server --reload --host 127.0.0.1 --port 8000
```

Во втором терминале:

```sh
cd web
npm ci
npm run dev
```

Vite на http://127.0.0.1:5173 проксирует `/api` к FastAPI. Документация API: http://127.0.0.1:8000/docs. Проверки из корня активированного окружения:

```sh
python -m pytest -q
python -m pip check
npm --prefix web test
npm --prefix web run build
git diff --check
```

Для полного локального набора задайте `CAREER_QUEST_KIT_DIR` абсолютным путём к четырём оригинальным файлам. Без переменной проверки внешнего набора пропускаются; CI использует небольшие независимые синтетические fixtures. Подробный совместный сценарий и команды — в [INTEGRATION.md](docs/INTEGRATION.md).

## Архитектура и доступ

React → REST → FastAPI → SQLite; AI-адаптер работает только на backend. `server/app/domain/` отвечает за прогресс и eligibility, `kit_schemas.py`/`kit_import.py` — за kit-v1, `ingest.py` — за demo-v1, `import_service.py` — за атомарную замену исходного demo. `web/src/` содержит API-клиент и UI. Бизнес-результаты и обновлённый профиль всегда приходят с сервера.

Сессия — `HttpOnly`, `SameSite=Strict` cookie; frontend использует `credentials: same-origin`. Изменяющие запросы требуют `X-Requested-With: CareerQuest` и разрешённого Origin, включая ручные запросы из Swagger/curl. При раздельном deployment нужен reverse proxy с общим origin. POST import/completion автоматически не повторяются: после сетевой ошибки сначала обновите данные.

Сотрудник видит только собственный профиль; HR читает профили, агрегаты и выполняет импорт, но не завершает активности за сотрудника. `DEMO_MODE=true` позволяет выбирать синтетические аккаунты и предназначен для локальной защиты. При `DEMO_MODE=false` демонстрационный вход отключён; корпоративная авторизация пока не реализована. Сервер по умолчанию слушает loopback. Для HTTPS нужен `COOKIE_SECURE=true` и явный `ALLOWED_ORIGINS`.

`.env`, ключи, SQLite, логи, зависимости, build/cache, `data/private/` и `/career_quest_dataset/` исключены из Git. Публичных рейтингов сотрудников нет. Личные достижения — необязательное оформление; они не меняют навыки, грейд или доступ. Полная казахская локализация, SSO, PostgreSQL/миграции и учёт денежных расходов AI остаются за рамками текущей реализации.
